## 3. Tests and results

Run: `dotnet test tools/DomainHarness/Tests/Game.Domain.Tests.csproj` (NUnit 3.14, .NET 8).
**61 passed, 0 failed**, about 1 s. Build has 0 warnings with warnings treated as errors.
One `[Explicit]` replay helper is skipped by design.

- Unit tests: RNG (5), config validation (9), merge (10), generators (8), inventory/sell/deliver/rewards/unlock (9), snapshot (4), ledger (6).
- Simulation: 8 seeds x 10,000 random actions on the 7x9 board, plus 10,000 on a 3x3 board with no
  inventory (board-full stress), plus a reproducibility check. Every step runs the invariant checker,
  with a full ledger replay every 250 steps. Every refused command is checked to leave the state
  byte-for-byte unchanged. Actions: spawn, drag/merge/swap, inventory in/out, sell, deliver (with
  corrupt inputs), enqueue/claim reward, time advance, save/load, kill-mid-drag-and-reload, stale
  drag, unlock, expand, garbage input. Failures print the seed, step and last 25 actions.
- Typical run (seed 1): 472 merges, 1,305 spawns, 611 reloads, 304 interrupted drags, 519 sales, 227 deliveries.
- **Harness self-check:** I planted three bugs in the engine, one at a time: a merge that leaves the
  dragged item tracked, ID reuse after load, and a board-full tap that spends a charge. The simulation
  caught each one and printed a replayable seed. The engine was then restored.

## 5. Known issues and risks

- **No Unity project files yet** (`ProjectSettings/`, `Packages/`). Setup steps are in `README.md`.
  `.meta` files will be generated by Unity and should then be committed.
- On the 7x9 board the simulation never fills the board (peak about 36 items). Board-full handling is
  covered by the 3x3 simulation and a dedicated unit test.
- The ledger grows without bound; it is intended for tests and debug builds only.
- Generator recharge is "deplete, cool down, refill to full". Per-charge trickle recharge is not
  supported. Tell me if the design needs it.
- Swap on a non-mergeable drop is my assumption of the genre default. Easy to change if you prefer
  "bounce back".
- Deliveries take items from the board only, not from inventory. Also my assumption.
- Clock tampering: cooldowns use caller-supplied time. The server-time check is planned for Services.
- `TryDeliver` allocates a small array per call (not a per-frame path).
